**Subject: ECS Electron — Apple Music Widevine licensing requires Media Foundation CDM identity; classic L3 CDM challenges rejected (status -1021). Need MF CDM support/distribution in ECS.**

Hi castlabs team,

We build **WaveForge**, a desktop music player for Windows running on your **castlabs ECS Electron** runtime (Electron 42.6.0, component updater active). We're integrating **Apple Music full-stream playback** using the same flow as music.apple.com's web player (MusicKit JS): `webPlayback` → CENC HLS variant → Widevine EME → `acquireWebPlaybackLicense`.

## Current status

The entire pipeline is implemented and verified down to byte-level parity with MusicKit JS:

- `webPlayback` returns CENC (rphq) HLS manifests for our test content ✓
- License request body/headers/URL are identical to what MusicKit JS sends from Chrome on the same machine (verified by capture diff) ✓
- Our developer token + media-user-token pair is valid: presenting a **challenge generated by a working CDM** together with our tokens to `acquireWebPlaybackLicense` returns **HTTP 200 with a license** ✓

## The blocker

The challenge generated **inside our ECS Electron** — by the classic software L3 CDM component (`widevinecdm.dll`, WidevineCdm 4.10.3050.x, delivered/seeded via CUS or from Chrome/Edge components) — is **rejected by Apple's license server**:

```
HTTP 200
{"errorCode":-42605,"status":-1021}
```

MusicKit JS maps **-1021 → WIDEVINE_CDM_EXPIRED**. The rejection follows the challenge, not anything else in the request (controlled experiment matrix below).

## Controlled experiment matrix (same machine, same network, same Apple account)

| # | Challenge source | dev token | media-user token | Result |
|---|---|---|---|---|
| 1 | Chrome's Media Foundation CDM | Chrome | Chrome | **200 — license issued** |
| 2 | Chrome's MF CDM | Chrome | ECS-captured token | -1002 (session ended) |
| 3 | ECS classic L3 CDM | ECS-captured | ECS-captured | **-1021** |
| 4 | ECS classic L3 CDM | Chrome | Chrome | **-1021** |

Reading: our token pair is valid (#5-analog and #1 issue licenses with matching sessions); **the rejected element is the classic software L3 CDM identity embedded in the challenge**. Chrome on the same machine plays Apple Music fully because Chrome 151+ on Windows now uses the **Media Foundation Widevine CDM** (`MediaFoundationWidevineCdm`, Google.Widevine.CDM.dll 1.0.2738.0) instead of the classic component.

Notably, our classic CDM *is* Irdeto-provisioned (the challenge contains an Irdeto-signed device certificate), yet is still rejected — suggesting Apple now requires the MF CDM identity class on Windows.

## What we need from castlabs

1. **Confirmation**: does the current ECS Electron for Windows support the **Media Foundation Widevine CDM** path? We can see `MediaFoundationCdmFactory` / `MediaFoundationCdmModule` / the `kMediaFoundationCdm` service sandbox compiled into our ECS binary, but EME still activates the classic CDM.
2. **Component distribution**: can the `MediaFoundationWidevineCdm` component (Google.Widevine.CDM.dll) be delivered via the ECS component updater — or provided for **bundled/offline distribution** in our installer? (Our target users are in China where castlabs/Google CDNs may be unreachable, so offline bundling matters.)
3. If MF CDM is not (yet) supported in ECS: is there a **pre-provisioned classic CDM** variant whose identity Apple accepts, and how do we obtain it for our builds?
4. Activation guidance: feature flags / browser-layer wiring in Electron needed for the MF CDM path (component registration format in Local State, `MediaFoundationCdmModule` CDM path provisioning, etc.).
5. Commercial note: we'd also like confirmation of what's required on the licensing side to bundle/distribute the CDM component with our installer.

## Environment

- castlabs ECS Electron 42.6.0 (Windows 11 24H2, x64)
- Classic CDM component: WidevineCdm 4.10.3050.0 / 4.10.3050.1 (also reproduced with components seeded from Chrome 151 / Edge 152)
- Reference working CDM: Chrome's MediaFoundationWidevineCdm 1.0.2738.0 (same machine)
- Reproduction script attached (`probe-apple-widevine-license.cjs`)

Thanks — happy to provide traces, tokens-for-testing, or a live repro session.

WaveForge team

## Addendum (2026-08-30 同日晚): ECS 42.6.0 内 MF CDM 扩展点的运行时实测证据

我们进一步翻查了随包文档与 ECS 二进制，发现 MF CDM 通道**存在但被层层锁住**。以下事实让上面的提问可以被具体回答：

1. **components API 运行时暴露了 MF 组件 ID**：`components.MEDIA_FOUNDATION_WIDEVINE_CDM_ID === 'neifaoindggfcjicffkgpmnlppeffabd'`（经典 CDM 为 `components.WIDEVINE_CDM_ID === 'oimompecagnajdejgnnjijobebaeigek'`）。与随包文档 docs/api/components.md 一致："Google Widevine Windows CDM (experimental) … currently disabled in releases builds"。
2. **CUS 拒绝对匿名安装下发该组件**：全新 profile 上 `components.whenReady([MEDIA_FOUNDATION_WIDEVINE_CDM_ID])` 立即 rejected（错误详情可另行提供）。同机同网络下经典 CDM 经 CUS 安装正常。
3. **二进制内存在 Chromium feature 开关**：`MediaFoundationWidevineCdm`，以及 `media_foundation_cdm_path` 参数名与 MediaFoundationCdm* 代码路径（MediaFoundationCdmFactory/Module/Data/Store）。
4. **feature + media_foundation_cdm_path 参数会让启动阻塞**：我们把参数指向 Chrome 的 Google.Widevine.CDM.dll 1.0.2738.0（原始路径与 URL 编码路径各试一次），browser process 始终到不了 ready；只开 feature 不带 path 参数则启动正常。参数语法/加载时序是否受支持，请确认。

由此，具体问题升级为：

- 需要什么授权（EVS 账号 / license 等级 / 构建开关）才能让 **CUS 向我们的安装下发 `neifaoindggfcjicffkgpmnlppeffabd` 组件**？
- MF CDM 就位后，EME 选择 MF CDM 的**受支持的浏览器层接线方式**是什么（feature + 参数语法、Local State 注册格式）？(4) 中的启动阻塞是否符合预期？
- 若 MF CDM 分发涉及商业安排，流程与条件是什么？

历史 MF 组件/EME 探针已在官方确认该路径废弃后删除；当前唯一保留的决定性复现脚本为 `scripts/probe-apple-widevine-license.cjs`。
