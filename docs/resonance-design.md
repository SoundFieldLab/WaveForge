# 共振（多人一起听）设计稿 — 隐形问题逐个钉死

> 面向实现的设计决策。每个问题给出**决策 + 理由 + 落到哪一层**，实现完按最后一节逐条复查。
> 对照：网易云「一起听」逆向见 docs/resonance-netease-listentogether-reference.md。

## 0. 一句话定位

房主就是服务器：局域网内房主进程起一个**只转发密文的星型中转**，成员各用自己的账号与音源播放同一队列；
房间只同步「放哪首、播到哪、谁在听」，**永不传输音频、永不共享会员**。

## 1. 权限与可用性：没有会员/没登录怎么办

**决策：进房间不设门槛，能不能出声是本机的事。**

| 情况 | 行为 |
|---|---|
| 完全没登录任何平台 | 可进房、可看队列、可聊天、可投票；本机**静音跟随**，播放区显示「未登录任何平台 · 已静音跟随」+ 「去登录」按钮 |
| 登录了但没会员 | 同上；对该曲显示「需要 VIP（你有 free）」，可发起跳过投票 |
| 部分平台有会员 | 本机解析时**优先用有权限的平台**（fusedSources → 本平台搜索 → 实测 getSongUrl），选不到就进入静音跟随 |
| 房主也没权限 | 推歌前预检：设置项「只推我能播放的歌」默认开；若关掉，推送时提示「其中 N 首你自己也听不了，仍要推送？」 |

**不做试听兜底（30 秒片段）**：会造成"我这边只有 30 秒"的割裂，比静音更糟。宁可明确告知 + 投票跳过。

静音跟随不是"假装在听"：UI 明确写「已静音跟随 · 1 首无法播放」，并提供「查看原因 / 发起跳过」。

## 2. 跨平台与版权：A 有、B 有、C 都没版权

- 成员**各自解析**：拿规范键（标题+歌手）与房子的候选源，在自己已登录且有权限的平台里找同款；
  校验顺序：`fusedSources` 命中 → 该平台搜索（现有 searchSongs）→ `getSongUrl` 实测可播 → 会员档校验（`entitlementSatisfies`）。
- 解析结果三态：`playable` / `locked`（要会员、无版权）/ `missing`（该平台没这首）。
- 上报给房主：`cannot-play { trackKey, tier, reason }` → 房主成员列表里该成员出现**⚠ 角标**，房间顶部出现一条**非阻塞提示条**（不是弹窗）：
  「@某人 无法播放这首 · 发起跳过」。点击 → 直接投票。
- **自动跳过投票**：当"无法播放"的在线成员 ≥ 一半时，房主自动发起跳过投票（客观信号，不必等人手点）。
- 房主自己的视角：永远能看到"当前曲目在 X/Y 位成员可播"。

## 3. 千首歌单：进房不能卡

- **协议不整包发队列**：`state` 只带 `queueSummary { total, firstKeys[≤50], cursor, mode }`；明细走 `queue-page { offset, limit }` 分页拉取（每页 50）。
  入房首包因此恒定小（≤ 几 KB），与歌单大小无关。
- **推送上限**：单次整单推送默认截断 200 首（设置项 100/200/500），提示「已取前 200 首」。
- **广播节流**：状态变更合并到 500ms 一次；播放进度单独 2s；心跳 2s。
- **UI 虚拟列表**：队列只渲染视口内 ~20 行（自己实现最简窗口化，行高固定 56px）。
- 房间队列硬上限 300（模型里已有），超出提示"房间队列已满"。

## 4. 半途加入：续接还是等下一首

- 默认**续接**：入房后按房主当前进度对齐（`positionMs + 已经过时间`），1.5s 淡入避免突兀出声；剩余 < 30s 则等下一首（不打断）。
- 设置项「入房行为：续接当前进度 / 等下一首」。
- UI 在播放区显示「正在续接《xxx》2:13」。
- 掉线重连同此逻辑（`restore` 语义）。

## 5. 平台时长不一致

- 匹配阶段用 `trackDurationCompatible`（±15s）排除 live/翻唱等明显不同版本。
- 同步用**绝对位置**（不是百分比）：`positionMs + elapsed`。
- 若成员版本比房主短：成员进到自身时长的 95% 时**钳制**（停在尾部不提前跳），并显示「版本时长不同 -8s」；
  切歌永远以房主为准（房主到尾 → 全体下一首），成员不等自己的尾部。
- 若成员版本比房长长：正常播放，等房主切歌。

## 6. 暂停/快进：b/c/d 怎么跟

- 房主权威：播放/暂停/seek 都是**硬同步**（立即对齐），成员端弹一条 1.5s 的轻提示：「房主暂停了」「房主快进到 2:10」。
- 成员操作按钮：默认「仅房主可控」→ 成员点播放/暂停/seek 时按钮不置灰，而是提示「房间由房主控制」并提供**申请控制**：
  房主收到请求 → 右下角 toast「@某人 申请控制播放 · 允许 5 分钟」，一键允许 → 该成员获得 5 分钟控制权（带到期时间，到期自动收回）。
- 房主可在房间设置里直接打开「允许所有成员控制播放」（默认关）。
- 控制权用 `controllerId + controllerUntil` 表达，**权威仍只有一人**（同一时刻只有一个 controller），交接不需要改 term。

## 7. 加歌 / 减歌 / 搜歌 / 歌单加（交互）

入口：房间底部「＋ 加歌」（Party 与 我推荐 可见；共享歌单模式仅房主可见）。

面板三个标签页：
1. **搜索**：复用现有搜索能力（分平台 + 融合结果），点行 → 加入队列（成员=请求，房主=直接入队并置顶到"下一步播放"可选）
2. **我的歌单**：列出本机已登录平台的歌单（复用 ExploreView 的 userPlaylists 数据源），支持「整单加入（截断上限）」与「多选单曲加入」
3. **我喜欢 / 最近播放**：一键整列加入

队列行操作：
- 房主：行尾 ⋯ → 置顶（下一首播放）、移除、复制歌名
- 成员：行尾 ⋯ → 移除**自己点的**、复制歌名
- 我推荐模式：只有轮到你时「＋」可用，顶部显示「轮到你推荐（还可加 2 首）」，其他人显示「等待 @某人 推荐」

减歌：`removeTrack(state, peerId, trackKey)`；房主任意移除，成员仅限自己点的（模型里校验）。
若移除的是当前播放曲目 → 房主切到下一首并广播。

## 8. 免责声明（首次进入共振，5 秒）

全屏卡片，5 秒倒计时后按钮才可点，可勾选「不再提示」（写 `waveforge:resonance-notice-ack`）。

**文案（中文）**

> **共振 · 一起听**
>
> 1. **各区各自播放**：房间只同步「放哪首歌、播到哪一秒」。音频永远来自你自己的账号与设备，成员之间不传输任何音频。
> 2. **不绕会员**：任何人的会员权益都不会被共享。你听不了的歌就是听不了——我们会告诉你原因，并可以发起「跳过此曲」投票（当前在线人数 8 成同意即跳过，房主可直接强制跳过）。
> 3. **不经服务器**：房间内容端到端加密（XChaCha20-Poly1305），局域网中转只转发密文，我们不运营任何服务器、不做任何统计。房间密钥由房主生成，因此**房主在技术上可以解密房间内容**（与群聊主持人相同）；房间指纹 `🍎 🍋 🍇 🍒` 可用来当面核对。
> 4. **只分享必要信息**：房间内可见的只有你的昵称与「已登录平台 / 会员档位」徽章。平台账号、Cookie、音源地址永远不会发出去。
> 5. **听歌礼仪**：上限 15 人，仅限朋友一起听；请勿用于公开传播或商业用途。

（按钮：`我已了解，开始使用`；倒计时中显示 `请阅读（剩余 5s）`）

**同步写入插件「使用须知」**（PluginCenter 的 requireNotice 机制），内容与上文一致的精简版 + 「不绕会员 / 不传音频 / 无服务器」三条硬承诺。

## 9. 房间设置（只放真正会影响行为的）

| 设置 | 默认 | 作用 |
|---|---|---|
| 昵称 | 本机用户名 | 房间内可见 |
| 默认房间模式 | Party | 创建房间时的预选 |
| 我推荐每人配额 | 2 | 我推荐模式每轮可加 1–3 首 |
| 单次推送歌单上限 | 200 | 100/200/500，防大歌单卡顿 |
| 只推我能播放的歌 | 开 | 推前预检，避免把整房带进死胡同 |
| 入房行为 | 续接当前进度 | 续接 / 等下一首 |
| 允许成员控制播放 | 关 | 打开后成员可暂停/快进（带节流） |
| 允许局域网发现 | 开 | 关掉则只能靠邀请串加入（更隐蔽） |
| 中转端口 | 25570 | 高级项 |
| 显示我的平台徽章 | 开 | 关掉则只显示昵称（更隐私） |
| 房间人数上限 | 15 | 2–15 |

以上全部登记进 `globalSettingsRegistry` 的 `network` 组（AGENTS.md 的硬要求），并在共振模式内提供同样的设置入口。

## 10. 性能 / 网络 / 安全 复查清单（实现后逐条过）

**性能**：入房首包大小与队列长度无关；状态广播节流 500ms；进度 2s；队列虚拟列表；大歌单截断；UI 不因 15 人成员列表重排而抖动（成员按 seat 稳定排序）。

**网络**：单条消息 ≤ 64KB（中转强制）；断线重连（房主断开→成员看到明确状态；成员断开→房主 6s 标记离线并保留席位）；15 人星型 = 房主 14 条连接；中转只准入 15 席。

**安全**：端到端加密（密钥 HKDF 自邀请串种子派生，中转拿不到种子）；信封 AAD 绑房间/发送者/类别/序号；防重放；匿名 `/discover` 不泄露房间号与房间码；房间码 6 位仅作中转第二道门；不记录载荷日志；无遥测；不传音频、不外发音源 URL 与 Cookie；房主可一键换房间码（怀疑泄露时）。

**逻辑**：共享歌单房主退出即结束；其他模式房主退出按 seat 交接并 term+1（旧权威消息丢弃）；最后一人退出即结束；成员退出保席位（可重连）；我推荐模式配额与轮次；投票阈值按**在线人数**算；切歌清空投票。

**交互**：所有错误都用**非阻塞提示条 / toast**，不用打断式弹窗；每个禁用态都给原因（title 或文案）；键盘可达（见下）。

## 11. 无障碍与键盘

- 房间内主要操作提供键盘快捷键：`空格` 播放/暂停（房主或获权成员）、`N` 下一首（房主）、`C` 聚焦聊天输入、`Esc` 关闭面板。
- 所有可点元素有 `aria-label`；投票/成员状态用 `aria-live="polite"` 宣告变化；配色沿用播放页的暗色玻璃质感，对比度满足正文 ≥4.5:1。

## 12. 与 App 的接线（避免重复造轮子）

- 播放控制：复用现成的 `waveforge:remote-control` 动作映射（`desktopControlHandlerRef`）。
- 队列替换：**当前不存在**，需新增（`setPlaylist` + `setCurrentIndex` + `bumpQueueRevision` 必须同批提交，否则播放器闪回主页）。
- 静音跟随：成员解析失败时不调用播放器，只更新 UI；解析成功但曲目被锁 → 播放器静音（volume 0）跟随，避免"我这边有声音别人没有"的错觉。
- 模式：`ViewMode` 增 `'resonance'`，同步改 `ModeSelectionPanel` / `ModeTransitionOverlay` / App 的 6 处白名单与分支；共振页内**不切走播放页**，房间播放条常驻底部。

## 13. 自审与实机验证中发现并修复的问题（2026-09-16 夜）

实机双实例（房主 + 成员，均静音）逐项走查 + 代码复查，发现并修掉以下 8 个问题：

| # | 问题 | 现象 | 根因 | 修法 |
|---|---|---|---|---|
| 1 | 人数上限被读成 2 | 房间显示 1/2 人 | `Number(localStorage.getItem(k))` 在键不存在时得 0，`Number.isFinite(0)` 通过，被夹到最小值 2 | 数值项统一走 `numberOrNull()`，区分「没设置」与「0」；加 7 条单测 |
| 2 | 成员加入后界面不刷新 | 数据已到位（房主看到 2 人），成员界面仍停在创建/加入大厅 | `reset()` 里 `listeners.clear()` 把 React 的 `useSyncExternalStore` 订阅清掉了 | reset 不再动订阅者；房间生命周期内组件持续订阅 |
| 3 | 消息风暴 | 几秒内房主收到 8000+ 条 `cannot-play` | 成员每收到一次状态就检查整队列并上报；房主收到上报又立刻再广播状态 → 回路 | ① 只在「当前曲目变化」时检查；② 只查当前 + 下一首；③ 同一首只检查/上报一次；④ 房主收到上报不再立刻广播（随周期状态带出）；⑤ 出站限流 30 条/秒兜底；加回归测试 |
| 4 | 聊天回声与错署名 | 成员发一句话，看到自己的一条 + 房主名义的同文一条 | 房主转发聊天时 ① 也发回给发送者 ② `broadcast` 用自己的昵称覆盖了原作者 | 转发时排除发送者（`others:<peerId>`）、保留原昵称；加回归测试 |
| 5 | 成员投票被丢弃 | 成员投票，双方都看不到票数 | 成员有两套 peerId（中转分配 vs 会话生成），房主成员表记的是前者，投票按后者判「非成员」 | 成员连接后**采纳中转分配的 peerId 作为身份**；房主侧对两种 id 都认 |
| 6 | 房主自己的投票丢失 | 房主投票不计入票数 | 房主把投票消息广播给成员，自己不处理回环 | 房主投票直接在本地状态生效再广播状态；加回归测试 |
| 7 | 成员被误判离线 | 房主看成员一会儿在线一会儿离线 | Electron 后台窗口节流定时器，6s 心跳超时太激进 | 在线判定放宽到 30s，真正断线交给中转的 `peer-left` |
| 8 | 端口被占用时创建失败且报错原始 | 提示 `listen EADDRINUSE 0.0.0.0:25570` | 只尝试一个端口，错误未翻译 | 从设定端口起自动顺延 10 个端口并 toast 告知；全部占用时给「请在共振设置里换一个端口」的人话提示 |

另外顺手加固：中转在 `stop()` 之后收到迟到消息不再读空房间（原会抛 `Cannot read properties of null`）。

**实机验证记录（均为静音，音量置 0，全程无播放）**

- 首次进入共振：5 秒倒计时按钮禁用（"请阅读（剩余 3s）"）→ 到点可点 ✓
- 房主创建 Party 房间：中转在 25570 运行，房间码 6 位，邀请串含 `#<code>.<secret>`，房间内可见可选择复制 + 二维码 ✓
- 成员用邀请串加入：双方成员列表 2 人且都在线；队列同步；`online: 2` ✓
- 聊天：成员一条消息在双方都只出现一次，署名正确 ✓
- 投票：成员一票 → 未过阈值；房主补一票 → 达到（2 人 × 80% = 2）→ 通过并切歌 ✓
- 免登录成员：本机解析失败 → 静音跟随 + `unableToPlay` 标记，不打断其他人 ✓
- 房主解散：成员房间关闭并回到大厅，提示原因 ✓
- 全程 `document.querySelectorAll('audio,video')` 无播放中的媒体 ✓

## 14. 第二轮返工（2026-09-16 上午，按用户逐条反馈）

### 14.1 修掉的真 bug

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 加歌面板打开任何歌单都是「这个歌单没有读到曲目」（「我喜欢」干脆点了没反应） | `getPlaylistDetail` 的返回形状**因平台而异**：apple/kugou/soda/spotify 给 `tracks: Song[]`，而 netease 给 `{playlist:{tracks:[原始字段 ar/al/dt]}}`、QQ 给 `{songlist:[原始字段 singer/interval]}`。面板只读 `data.songs` → 永远空数组 | 新增 `src/utils/playlistSongs.ts` 的 `playlistDetailSongs(data, platform)` 统一收口（含 QQ 秒/毫秒换算、封面包 url 拼接、空壳过滤），面板两条路径都改用它；加 6 条单测 |
| 2 | 渲染进程一重载，就再也建不了新房（报「房间已在进行中」） | ①`session.reset()` 里 `transport.close()` 是同步的，而它触发的 `bridge.stop()` 是异步 IPC，紧接着的 `bridge.start(新房间号)` 撞上还活着的旧房间；②重载后旧房间成了主进程里的僵尸 | ①`close()` 改为可 await，`create()`/`join()` 先 `await releaseRelay()` 再 start（join 强制停，成员不该挂着中转）；②中转自身加固：**空房间**（无房主连接、无成员）允许被新房顶掉，有人在线时仍拒绝；加 2 条 node:test |
| 3 | 房间里改了「昵称来源」或自定义名，名册还显示旧名字 | 名册只在 `joinRoom` 时写入，`joinRoom` 对同 peerId 是幂等返回旧成员，改名没有通道 | 新增 `updateMemberProfile()`（席位/入房时间不变，无变化返回 null 不广播）；`hello` 收到已存在成员时更新名册；`session.setIdentity()` 变化时房主广播状态、成员重发 `hello`；加模型测试 |

### 17.2 缺失的功能：房间下一首预热

**这是真缺口**：共振的播放权威在房主手里，本机只在自己的 `apply` 收到新 `trackKey` 时才去解析并加载那首歌——
而其它模式走的是 `preloadUpcomingSongs`（歌词 + 封面 + 音频地址 + 无缝播放备用音轨）。所以房间里换歌会比其它模式慢一拍，
首次播放某首歌时尤其明显（要现搜索、现取流）。

修法：新增 `preloadResonanceTrack(track)`，与其它模式的「下一首预载」同一套内容（`ensureSongLyrics` + `preloadArtwork(role:'player')`
+ `getSongUrl` 写入 `preloadCacheRef`），在这三处调用：
- 适配器 `setQueue(tracks, startIndex)` → 预热 `tracks[startIndex + 1]`（入房/队列更新时）
- 适配器 `apply()` 里换歌分支 → 预热房间队列的下一首
- 内部 `Set` 去重，同一首只预热一次；只解析与取流，**不写 App 播放列表、不改播放状态**（房间队列语义不变）

**实测证据**（同一房间、同一解析函数 `resolveResonanceTrackCached`）：
被预热过的下一首 `canPlay` 用时 **0ms**（命中缓存），未预热的对照曲目用时 **12335ms**。这 12 秒就是房间里换歌时会白等的时间。

### 17.3 关于会员档位的边界

- **Apple Music**：订阅制，登录即 `vip`（已修）。
- **酷狗**：仓库里没有任何可用会员档位来源（`fetchKugouUserInfo` 只返回昵称/id/头像，网关只在报错里带 `vip_required`），
  因此保持 `unknown` = 「不预设，实测取流」。**故意不改成 `free`**：那会让付费曲在取流前就被判死成 locked，比实测更不准。
- 三档语义：`unknown` = 不预设（实测）；`free` = 确定免费号；`vip`/`svip` = 确定会员。matcher 里所有档位比较都显式放行 `unknown`。

## 19. 第七轮（2026-09-16 晚）：排除「页面 20px 溢出」误报，修主按钮被裁

### 19.1 页面 19~21px 溢出：是测试假象，不是缺陷

前一轮遗留的「页面稳定溢出 19~21px」在本轮复现了，但定位后确认**是自动化环境的假象**：

- 现象：`document.documentElement.scrollHeight - innerHeight` 稳定多 19~21px，且 `window.scrollTo(0, 500)` 真能滚到 19px；
- 根因：CDP 连接的页面处于**后台态**（`document.hidden === true`），浏览器把 `requestAnimationFrame` 节流到近乎停止（实测 1.5s 内只跑了 1 tick）。framer-motion 的进入动画因此**永远停在 `initial` 态**——共振视图容器停在 `opacity:0; transform: translateY(26px) scale(0.985)`，`inset-0` 高 989px 经缩放+位移后 bottom 到 1008，正好超出 19px。旧视图的 `exit` 同样推不动，所以探索页内容也一起挂在 DOM 里。
- 验证：发 `Emulation.setFocusEmulationEnabled` + `Page.setWebLifecycleState('active')` + `Page.bringToFront` 后 rAF 恢复（ticks 1→5，`visibility: visible`），**所有视口页面溢出均为 0px**（1613×989 / 1440×900 / 1280×800 / 1366×768 / 1280×720 / 1024×640）。
- 结论：稳态布局无溢出，`html/body { overflow-y: hidden }` 生效。**教训**：以后所有布局探针必须先强制页面 active，否则动画中间态会污染测量结果。

### 19.2 真 bug：「创建房间并开始」在矮窗口被顶出卡片可视区

| 项 | 内容 |
|---|---|
| 现象 | 1366×768 下主按钮被推到卡片可滚区下方 37px；1280×720 下 85px；而卡片用了 `wf-no-scrollbar` **隐藏了滚动条**，用户既看不到按钮也看不出还能滚 |
| 根因 | 整张卡片是一个滚动容器，内容 + 按钮共 684px 固定高；窗口变矮时按钮跟着内容一起被滚出可视区 |
| 修法 | 卡片改为 `flex flex-col`，内部新增内容区 `wf-no-scrollbar min-h-0 flex-1 overflow-y-auto` 承接滚动，主按钮移到滚动区**之外**并保持 `shrink-0` |

**实测（应用最小窗口 1200×800 与常见笔记本分辨率）**：主按钮在全部视口可见且底部留白稳定 25px；内容区溢出 1200×760 时仅 10px、1366×768 时 2px、≥1200×800 时为 0；「当前可用平台」行与人数滑杆在 1200×760 以上均可见。

> 注：窄+矮组合（如 900×600，低于应用 `minWidth/minHeight = 1200×800`）下两侧卡片会被压得很扁，内容区需内滚更多——属超出应用窗口约束的场景，不做额外处理。
