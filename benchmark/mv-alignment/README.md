# MV 对齐 · Live/现场版基准

针对「live/现场版 MV 能否对齐、偏移准不准」的离线评测。数据来自 `.tmp-kg-align/` 的大规模采集（生产口径：22050Hz 单声道 50fps 帧 RMS 包络），无需启动 app。

## 数据资产

| 文件 | 规模 | 说明 |
|---|---|---|
| `.tmp-kg-align/song-envs.json` | 2193 | QQ/网易歌曲包络（键=歌单 trackKey） |
| `.tmp-kg-align/mv-envs.json` | 5671 | 候选 MV 包络 + 标题/作者/类型元数据（键=bvid） |
| `.tmp-kg-align/candidates.json` | 1826 | 生产匹配函数产出的候选池（song→chain） |
| `benchmark/mv-alignment/live-eval-set.json` | 172 | live/现场类真实配对（标题 live 标记 ∪ type=live） |

## 三步评测

```bash
# 1. 逐对跑生产链路（全局锚 → 段落支持率 → 分段锚点），产出 live-eval-results.json
python benchmark/mv-alignment/eval-live.py

# 2. 三角证据预计算（全曲峰 / 段投票簇 / 恒定偏移支持率），产出 live-evidence.json
#    （慢：全范围段投票 × 172 对，约 10 分钟）
python benchmark/mv-alignment/build-evidence.py

# 3. 方案对比 + 门槛扫描（读 live-evidence.json，秒级）
python benchmark/mv-alignment/compare-gates.py
```

## 真值口径（三角验证）

现场版没有人工标注偏移，真值由 ≥2 条独立证据一致（±3s）构成：

1. **全曲包络峰**（peak ≥0.55）
2. **段投票强簇**（30s 段独立全范围扫描，r≥0.7 的簇，票≥2 或权重≥3）
3. **恒定偏移支持率**（30s 段相关 >0.4 的占比 ≥0.5）

证据矛盾或单证据 → 真值缺失（该对不可评，拒绝行为视为正确——宁缺毋滥）。

## 生产案例复盘：AM 动态封面过渡后卡旧曲 5-6s（2026-10-14）

**现象**：automix 过渡提交后，歌名/歌词/静态封面已切到下一曲，但**动态封面**还播着
上一曲的动画 5-6s 才换（Apple Music 动态封面用户实测）。

**根因**：`useAppleDynamicCover` 的查询 effect 在 trackKey 变化时用
`setState(prev => ({ cover: prev.cover, loading: true }))` **保留旧封面**直到新查询
返回（300ms 延迟 + 网络往返，缓存 miss 时 1-2s）——期间新曲静态封面被旧曲动画盖住。
静态封面走 `displayCoverUrl`（commit 帧已同步切换），动态图层是独立路径，漏了同步。

**修复**：hook 增加 `coverTrackKey` 追踪当前生效封面的归属——查询启动即清 cover
（不再 prev 保留），返回后登记归属；trackKey 与 coverTrackKey 不一致（查询在途/失败）
时立即清空，静态封面即时接管。旧行为"动画盖住新静态封面"不复存在。

**教训**：切换类 UI 的异步资源（封面/歌词/背景）在切歌瞬间必须**先清后取**，
"保留旧的直到新的就绪"只适用于同曲刷新，跨曲场景一律是串台源。

## 歌词三问题诊断与修复（2026-10-14）

**1. 逐字填充"卡"（点歌词跳转后，切歌恢复）**：
seek 触发 `cancelScheduledTransition` → automix 重规划链路（云端 MixPlan 往返 + 准备步骤）
抢占主线程 → 30fps 逐字 RAF 掉帧。切歌/切回不卡是因为分析结果已进内存缓存
（`current.analysis || analyze(...)`），不重算。已有缓解：seek 落在过渡起点**之前**时
保留旧计划不重排（`canReusePlan`）；落在窗口内/越过时确需重排（旧计划的时间轴已失效）。
进一步优化属底层结构改造（分析全离线化），记录在案。

**2. 点跳转歌词位置错位**：同一根因的视觉面——seek 瞬间 `currentTime` prop 已更新，
但滚动定位用平滑时钟的最后一帧，重分析窗口内掉帧放大了间隙。切歌重建歌词数组强制
全量重排所以恢复。

**3. 翻译错位（A Moment Apart 开头挂别句翻译）**：两处叠加——
   a) `mergeLyricsWithTranslationAndRoman` 的元数据白名单 `/^(词|曲|编曲|作词|作曲|演唱|歌手)[：:]/u`
      **只认中文**，AM 的 'Lyrics by: X'/'Produced by: X' 英文元数据行被当正文参与贪婪匹配；
   b) 开头放宽阈值过大（翻译 2s、罗马音 3s）——足以跨过整句，密集的元数据行互相抢翻译。
**修复**：
   - 新共享工具 `src/utils/lyricCreditLine.ts`（中/日/英署名标记 i18n 正则，含 lyrics by/
     produced by/mixed by/mastered by/written by 等），`musicApi` 两处（isMetadata 判定、
     isMetadataOnlyLyrics 空壳判定）统一接入；
   - 开头放宽阈值收紧：翻译 2s→1.2s，罗马音 3s→1.5s / 2s→1.2s（时间戳抖动的真实
     幅度 <0.5s，原放宽足以跨句）。

## 音质切换语义（2026-10-13）

**"实际在播"不跟随所选档位**的根因:URL 缓存/预载缓存都会在音质事件时失效,但**正在播的
这首歌没有任何代码重载 audio.src**——切换只影响下一首。

**修复**:
1. **重载当前歌**:音质事件时若在播放中,重新 `loadAndPlaySong`(按新档取流),保留播放
   位置(seek 回 原位置-0.35s)与播放态;
2. **electron 下载缓存清理**:automix 分析/渲染与 MV 对齐共用的音频文件按 trackKey(mid)
   落在 electron 下载缓存,**音质不掺 key**——音质变更时旧音质文件会被复用(automix 仍按
   旧档分析/渲染过渡)。音质事件时按当前+预载 trackKey 删除缓存文件,下一轮 automix/对齐
   自然按新档重下。

**刻意不做的**:trackKey 掺音质指纹——会让 automix 分析/渲染缓存、对齐缓存全部失配,
代价远大于收益。

## 生产案例复盘：冷选歌曲背景残留/封面残留（2026-10-13）

**现象**：手动从探索页/其他歌单冷选下一首时，背景 MV 长时间不来；有时上一首 MV 画面
"残留"在新歌封面上（Apple Music 动态封面尤其明显——图层叠加式封面非不透明底，
旧视频帧直接穿透）。

**日志证据**（automix-backend.log）：
1. `Error occurred in handler 'audio-download:prepare': Error: Invalid track key` +
   `歌曲包络解码失败`——昨夜的 `decodeSongEnvelope` 把**完整代理 URL** 当 trackKey
   传给 `prepare`：electron 侧缓存索引/403 冷却按 trackKey 组织，URL 作 key 既污染
   语义也在打包版被入口校验拒绝（幽灵级难查：dev 与打包校验路径不一致）；
2. 同一首歌 `歌曲包络解码失败：Failed to fetch` 复发 → 拍点网格 0.309<0.5 被拒 →
   拖到 30s 后媒体元素兜底；
3. `匹配完成 best=none` ×3（冷选歌曲候选池空）→ `回退封面 进入 status=none` 但
   **视频槽未清**，上一首 MV 帧挂在槽里穿过封面层。

**修复**：
- `getSongEnvelope` 增加 `cacheKey` 参数：调用方传 songKey 域稳定 ID（`qq:123`），
  缺省退 `env:`+URL 哈希——URL 不再作 trackKey；`probeCandidateIdentities` 双入口
  （背景层/看歌层）透传 songKey；
- `status=none/error`（回退封面）时**清空双槽**：pause + removeAttribute('src') + load、
  slotBvid/slotPlayState 复位、paintedSlots 归零——旧帧立即从视觉层消失，封面层干净接管。

## 模型深化：投票真值仲裁（2026-10-13，6008 对全量证据）

采纳后质量审计发现:95% 采纳对误差 ≤0.1s(搜索网格粒度顶格),但 98 对误差 0.5-3s 的
中误差样本有一个鲜明签名——**峰 0.47-0.55(支持率采纳,非同录音级)+ 段投票与峰反向
1.5-4.5s + 支持率偏低**。逐对核对:真值几乎总在投票侧(Ex/Villain/Bad Apple/
Rage Beneath the Mountains 群,峰位误差 3-4.5s、投票位误差 0)。

**机理**:重复结构歌曲(phonk/副歌)的全曲互相关 argmax 会落在"错误重复段"上形成假峰;
段投票是 30s 段独立局部扫描,多数段仍锁定真偏移。峰越弱(非同录音级)、投票的独立
信息量越大。

**仲裁规则(已落地)**:峰 <0.6 且段投票与峰矛盾 >1.5s 且支持率 <0.45 → 采纳投票偏移。
6008 对基准:净挽回 73.5s 误差(增益 94.6s/损失 21.1s = 4.5:1)、FP 67→64、
**≤2s 99.0%→99.5%**。峰≥0.6(同录音)或支持率≥0.45(结构证实强)时峰仍优先——
投票以峰为先验扫描,强峰证据下投票无独立信息量(直接平均反而全面劣化,已否决)。

实现:`detectViaBeats`/`computeLiveCompensation` 双路径仲裁,分段锚点随仲裁偏移重算。

## 生产案例复盘：MV 对齐"慢半拍/卡顿"（2026-10-13）

**体感**：有时 MV 落后歌词一两秒("慢半拍")、有时对齐生效时画面猛跳一下("卡一下")，
有时又完全正常——不稳定。

**时序链剖析**（三个延迟/跳变源）：
1. **首跳竞态**：对齐算完时视频常还在缓冲（readyState<2），一次性跳转被跳过后，只能等
   1.5s 粒度轮询——而轮询校正还要求漂移>3s+冷却≥10s，最坏拖 10s+；
2. **小漂移不修**：轮询只管 >3s，0.8-3s 的"慢半拍"区永远挂着；
3. **硬 seek 卡顿**：每次校正都是 currentTime 赋值 = 重缓冲。

**修复**（BilibiliMvBackground.tsx）：
- **事件即时对齐**：槽位视频 `playing/canplay` 事件触发即时对齐跳转（+50ms 让时钟稳定），
  视频一就绪就在位，不再依赖轮询兜底；
- **平滑追频**：0.8-3s 漂移不再硬 seek，而是 playbackRate 微调（≤5%，漂移/60 比例），
  40s 内悄然归位、零重缓冲；追上（<0.4s）自动归 1；
- **与倍速系统协同**：微调写入 `bgRateTrimRef` 乘在用户倍速上（applyToSlots 统一应用），
  倍速设置/追频两系统不再互搏；seek 后微调归 1 重新起算。
- <0.8s 在人眼相位差容差内，不动作（避免反复微调制造新的抖动）。

## 生产案例复盘：Ghost (tayori) 未对齐（2026-10-12）

**现象**：官方 MV(峰 0.494 网格) 前三分钟自由播放，30s 后媒体元素包络兜底才对上。

**根因链**：`getSongEnvelope`/`detectViaBeats` 用裸 `fetch(songUrl)` 下载 QQ 音频取包络 →
`Failed to fetch`（QQ 音频 URL 的 vkey 会过期/被过渡竞态打断）→ 拍点网格 0.494 因
「无包络证据」低于 0.5 门槛被拒（差 0.006！）→ 30s 后媒体元素兜底。

**修复**：新函数 `decodeSongEnvelope`——先走 `window.electron.audioDownload.prepare`
（automix 主链路同路，日志显示同一首歌 `Cache hit`，零网络）+ `waveforge-media://`
协议 fetch，失败再退裸 URL。`getSongEnvelope` 与 `detectViaBeats` 两处统一接入。

**教训**：automix 能下的音频，对齐链路必须也能下——两条链路的下载路径要共用。
